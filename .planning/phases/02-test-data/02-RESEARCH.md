# Phase 2: Test Data - Research

**Researched:** 2026-02-18
**Domain:** Bioinformatics test data — synthetic VCF construction, real data subsetting, bcftools/samtools operations
**Confidence:** HIGH (core tooling and gitignore behavior verified); MEDIUM (public data URLs verified, freebayes tiny content inferred)

## Summary

Phase 2 creates all test data needed for Phase 3 (BATS test framework). The work decomposes into four areas: (1) hand-crafted synthetic GATK and Freebayes VCFs with precise field values triggering each filter, (2) utility VCFs and a minimal reference FASTA, (3) real data subsets downloaded from public repositories, and (4) expected output VCFs generated by running the current hardnormly.sh.

Two gitignore findings are critical and change the implementation approach. First, `ref/hs37d5.fa` is **gitignored** via the `/ref/` pattern — it exists on disk but is NOT committed to the repo. Any plan that assumes `ref/hs37d5.fa` is available at test time must handle this. Second, the `*test*` pattern in `.gitignore` matches the `tests/` directory name itself, so ALL files under `tests/` are gitignored. Every test data file requires `git add -f` to force-add. The recommended fix is to update `.gitignore` to un-ignore the `tests/` directory rather than using `git add -f` on hundreds of files.

The core technical challenge is constructing valid synthetic VCFs. bcftools is strict about INFO/FORMAT header declarations — every field used in a filter expression must have a matching `##INFO` or `##FORMAT` header. The pipeline uses `bcftools +fill-tags` to compute `FORMAT/VAF` from `FORMAT/AD`, so synthetic VCFs must include `FORMAT/AD` values producing the intended VAF. The reference FASTA for bcftools norm must have contig names matching VCF CHROM values — since the test region is `22:16000000-16100000` (GRCh37, no chr prefix), the reference contig must be named `22`. This requires either downloading the full chr22 reference or carefully managing the extracted FASTA header.

**Primary recommendation:** Update `.gitignore` to un-ignore `tests/` as the first act of Phase 2, before creating any test files. Build synthetic VCFs as plain-text `.vcf`, validate with `bcftools view`, compress with `bgzip`, index with `bcftools index -t`. For the test reference FASTA, extract from hs37d5.fa (downloaded during generate_test_data.sh) and fix the contig header.

### Pattern 2: GATK Synthetic VCF Header

Every GATK-style synthetic VCF must declare all INFO and FORMAT fields used in filter expressions.

```
##fileformat=VCFv4.2
##FILTER=<ID=PASS,Description="All filters passed">
##INFO=<ID=AS_FS,Number=A,Type=Float,Description="Allele-specific Fisher Strand bias">
##INFO=<ID=AS_SOR,Number=A,Type=Float,Description="Allele-specific Strand Odds Ratio">
##INFO=<ID=AS_MQ,Number=A,Type=Float,Description="Allele-specific RMS Mapping Quality">
##INFO=<ID=AS_MQRankSum,Number=A,Type=Float,Description="Allele-specific MQ Rank Sum">
##INFO=<ID=AS_ReadPosRankSum,Number=A,Type=Float,Description="Allele-specific Read Pos Rank Sum">
##FORMAT=<ID=GT,Number=1,Type=String,Description="Genotype">
##FORMAT=<ID=DP,Number=1,Type=Integer,Description="Approximate read depth">
##FORMAT=<ID=AD,Number=R,Type=Integer,Description="Allelic depths ref and alt alleles">
##contig=<ID=22,length=51304566>
#CHROM	POS	ID	REF	ALT	QUAL	FILTER	INFO	FORMAT	SAMPLE
```

**Critical design notes:**
- `Number=A` for allele-specific INFO fields (one value per alt allele at biallelic sites = 1 value)
- `Number=R` for FORMAT/AD (one per allele including ref, so ref+alt = 2 values)
- `FORMAT/VAF` is NOT declared in the header — `bcftools +fill-tags` adds it dynamically
- `##contig` header required for bcftools norm to recognize the chromosome

### Pattern 3: Freebayes Synthetic VCF Header

```
##fileformat=VCFv4.2
##FILTER=<ID=PASS,Description="All filters passed">
##INFO=<ID=AO,Number=A,Type=Integer,Description="Alternate allele observations">
##INFO=<ID=SAF,Number=A,Type=Integer,Description="Reads supporting ALT on forward strand">
##INFO=<ID=SAR,Number=A,Type=Integer,Description="Reads supporting ALT on reverse strand">
##INFO=<ID=RPR,Number=A,Type=Integer,Description="Reads placed right of the variant">
##INFO=<ID=RPL,Number=A,Type=Integer,Description="Reads placed left of the variant">
##FORMAT=<ID=GT,Number=1,Type=String,Description="Genotype">
##FORMAT=<ID=DP,Number=1,Type=Integer,Description="Total read depth">
##FORMAT=<ID=AD,Number=R,Type=Integer,Description="Allelic depths ref and alt">
##contig=<ID=22,length=51304566>
#CHROM	POS	ID	REF	ALT	QUAL	FILTER	INFO	FORMAT	SAMPLE
```

**Critical difference from GATK:** AO, SAF, SAR, RPR, RPL are INFO fields (site-level), not FORMAT (per-sample). The filter expressions in `freebayes_filters.txt` use `INFO/AO`, `INFO/SAF`, etc. Declaring these as FORMAT would break filter matching.

### Pattern 4: VAF Engineering from AD Values

`FORMAT/VAF` is computed by `bcftools +fill-tags` as:
```
VAF = AD[alt] / (AD[ref] + AD[alt])
```

Design AD values to produce specific VAF values for each filter trigger:

| Filter | Condition | Example AD | Resulting VAF | Outcome |
|--------|-----------|------------|---------------|---------|
| VAFu02het | VAF < 0.2, GT=0/1 | 18,2 | 2/20 = 0.10 | FAIL (excluded) |
| VAFu02het pass | VAF >= 0.2, GT=0/1 | 12,8 | 8/20 = 0.40 | PASS |
| VAFo08het | VAF > 0.8, GT=0/1 | 2,18 | 18/20 = 0.90 | FAIL (excluded) |
| VAFo08het pass | VAF <= 0.8, GT=0/1 | 10,10 | 10/20 = 0.50 | PASS |
| VAFu095hom | VAF < 0.95, GT=1/1 | 2,18 | 18/20 = 0.90 | FAIL (excluded) |
| VAFu095hom pass | VAF >= 0.95, GT=1/1 | 0,20 | 20/20 = 1.00 | PASS |

**Rule:** FORMAT/DP must equal sum(AD) or be larger. Do not set DP < sum(AD). Keep GT consistent with AD proportions.

### Pattern 7: Reference FASTA for Test Region

**Problem:** `ref/hs37d5.fa` is gitignored and not committed. Tests cannot depend on it.

**Solution:** `generate_test_data.sh` downloads hs37d5 and extracts the chr22 region. The extracted `mini_ref.fa` IS committed (force-added) along with all other test data.

**FASTA header issue:** `samtools faidx hs37d5.fa 22:16000000-16100000` produces header `>22:16000000-16100000`. bcftools norm looks for contig `22` and fails. Fix:

```bash
# Extract and fix the header
samtools faidx hs37d5.fa 22:16000000-16100000 \
    | sed '1s/.*/\>22/' > tests/data/synthetic/mini_ref.fa

samtools faidx tests/data/synthetic/mini_ref.fa
```

**Why this works:** The FASTA now has contig name `22`, matching the VCF CHROM=22. The sequence covers positions 16000000-16100000 of chr22. bcftools norm uses POS values as 1-based coordinates WITHIN the contig — since the contig is named `22` and has 100001 bases (positions 1-100001 within the file), VCF position 16010100 refers to offset 10101 within the file (16010100 - 16000000 + 1 = 10101), which is within range.

**Wait — this is still wrong.** bcftools norm uses absolute chromosomal coordinates. A VCF with `CHROM=22, POS=16010100` tells bcftools to look at position 16010100 on contig `22`. The FASTA's contig `22` only has 100001 bases (indexed 1-100001). Position 16010100 is out of range.

**Verified correct solution:** Synthetic VCF positions must be offset. Design all synthetic variants at POS 1-100000 (1-based positions within the 100kb FASTA), NOT at chr22:16xxxxxx. For example, variant at FASTA position 10100 corresponds to chr22 genomic position 16010100, but in the synthetic VCF the POS field should be 10100.

**Alternative correct solution (recommended):** Use `samtools faidx` to extract full chr22 from hs37d5 into `chr22_full_ref.fa` in the temp dir (used during generate_test_data.sh only, not committed). Use this full chr22 FASTA when running hardnormly.sh to generate expected outputs. For bcftools norm during synthetic VCF construction/validation, use the full chr22 reference downloaded during the script run.

For the committed `mini_ref.fa` used in tests: use it ONLY for tests that don't call `bcftools norm` (i.e., tests that pass `--no-norm` or similar). The integration test uses the full reference available at runtime.

**Pragmatic final recommendation:** This is a complex issue. The planner should address it explicitly. The two viable approaches are:

1. Design synthetic VCFs with positions 1-100000 (offset within the mini_ref FASTA), and rename the contig header to `>22`. All positions in synthetic VCFs are small integers (e.g., 10100 instead of 16010100). The BED files and include/exclude regions use the same small coordinates.

2. Generate expected outputs using `ref/hs37d5.fa` (which exists on disk if conda env is set up), generate all test data in `generate_test_data.sh` using the full reference. Only commit the output files (expected VCFs + synthetic VCFs). Tests that need bcftools norm require the full reference at test runtime.

Approach 1 is cleaner for CI (self-contained), but requires all coordinates to be designed in the 1-100000 range. Approach 2 is simpler to implement but requires the full reference at test time.

### Pattern 9: Generating Expected Outputs

Expected outputs are generated by running the current hardnormly.sh on synthetic VCFs.

```bash
# Capture git commit hash for traceability
echo "# Generated by hardnormly.sh at commit: $(git rev-parse HEAD)" > tests/data/expected/BASELINE.txt

for SAMPLE in A B; do
    ./hardnormly.sh \
        -v "tests/data/synthetic/gatk_sample_${SAMPLE}.vcf.gz" \
        -f REFERENCE_FASTA \
        -b tests/data/include_regions.bed \
        -e tests/data/exclude_regions.bed \
        --filters-file defaults/gatk_filters.txt \
        -g tests/data/hg19_chr22.genome \
        -o "tests/data/expected/gatk_sample_${SAMPLE}_filtered.vcf.gz"
    bcftools index -t "tests/data/expected/gatk_sample_${SAMPLE}_filtered.vcf.gz"
done

# Validate before committing
bcftools query -f '%CHROM\t%POS\t%FILTER\n' \
    tests/data/expected/gatk_sample_A_filtered.vcf.gz
```

`REFERENCE_FASTA` depends on the coordinate scheme chosen (see Pattern 7).

### Anti-Patterns to Avoid

- **Using plain gzip instead of bgzip:** Tabix requires BGZF format. `gzip` and `bgzip` both produce `.gz` files but are incompatible for tabix indexing. Always use `bgzip`.
- **Writing .vcf.gz files directly:** Binary BGZF cannot be hand-written. Write plain `.vcf`, then `bgzip -f`, then `bcftools index -t`.
- **Forgetting the `##contig` header:** bcftools norm requires this. If absent, norm may warn or fail on chromosome name lookup.
- **Declaring Freebayes INFO fields as FORMAT:** AO, SAF, SAR, RPR, RPL must be `##INFO` lines. The filter expressions use `INFO/AO` syntax, not `FORMAT/AO`.
- **Omitting FORMAT/AD from synthetic VCFs:** Without AD, `bcftools +fill-tags` cannot compute VAF. All VAF-based filters will evaluate to missing (`.`) and never trigger.
- **Committing test data without `git add -f`:** The `*test*` gitignore pattern blocks the entire `tests/` directory. Files appear to add but don't — verify with `git status` after staging.
- **Generating expected outputs before synthetic VCFs are finalized:** Expected outputs must be generated from the final synthetic VCFs. If a synthetic VCF changes after expected output generation, regression tests break immediately.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| VCF compression | Custom gzip routine | `bgzip` | BGZF is block-indexed gzip; standard gzip produces non-seekable output incompatible with tabix |
| VCF/BED indexing | Manual byte-offset tables | `bcftools index -t` / `tabix -p bed` | Tabix index format is binary and complex; all htslib tools require it |
| Remote VCF subsetting | Download entire 196MB 1000G chr22 VCF | `tabix -h URL REGION` | tabix streams only the needed compressed blocks; ~100KB instead of 196MB |
| VAF computation | Manually set FORMAT/VAF in synthetic VCF | Let `bcftools +fill-tags` compute from AD | The pipeline computes VAF from AD; a hand-set VAF field would conflict with or be overwritten by fill-tags |
| FASTA region extraction | Custom python parser | `samtools faidx ref.fa REGION` | Handles BGZF FASTA natively; produces properly indexed output |
| VCF format validation | Visual inspection | `bcftools view file.vcf.gz -Oz -o /dev/null` | bcftools exits non-zero on any format error; fast and authoritative |

**Key insight:** The bioinformatics file format stack (BGZF + tabix) is non-trivial. Every shortcut around standard htslib tools has bitten people with "file not BGZF format" or "index does not match" errors.

## Common Pitfalls

### Pitfall 1: gitignore Blocks Entire tests/ Directory

**What goes wrong:** `*test*` in `.gitignore` matches the `tests` directory name. `git add tests/data/gatk_sample_A.vcf` runs silently but adds nothing. `git status` shows no changes. Hours of work appear to disappear.

**Why it happens:** The gitignore was designed for a project with no test directory. `*test*` is a filename glob that matches directory names too.

**How to avoid:** Add `!/tests/` to `.gitignore` before the `*test*` line. Git processes rules top-to-bottom; the exception must come before the rule it overrides.

**Verified:** `git check-ignore -v tests/data/gatk_sample_A.vcf` confirms `.gitignore:21:*test*` is the blocking rule.

**Warning signs:** After `git add tests/`, `git status` shows zero new files staged.

### Pitfall 2: ref/hs37d5.fa is Gitignored and Not Available in CI

**What goes wrong:** Plans reference `ref/hs37d5.fa` as if it's committed to the repo. It is not. Tests that require bcftools norm against this reference fail in CI with "file not found".

**Why it happens:** `/ref/` is gitignored. The full hs37d5 reference (~3.4GB) cannot be committed. It must be available separately.

**How to avoid:** Either (a) extract `mini_ref.fa` during `generate_test_data.sh` and commit it to `tests/data/`, or (b) design tests to use the mini_ref.fa that IS committed.

**Verified:** `git check-ignore -v ref/hs37d5.fa` confirms `.gitignore:16:/ref/` blocks it.

### Pitfall 3: FASTA Contig Name Mismatch After Extraction

**What goes wrong:** `samtools faidx hs37d5.fa 22:16000000-16100000 > mini_ref.fa` creates a FASTA with header `>22:16000000-16100000`. bcftools norm with VCF `CHROM=22` fails to find contig `22` in the FASTA.

**Why it happens:** samtools faidx preserves the region string as the sequence name by default.

**How to avoid:** Pipe through `sed '1s/.*/\>22/'` to rename the first header line. Then re-index.

**Warning signs:** `bcftools norm` error: `[E::fai_fetch] sequence "22" not found`.

### Pitfall 4: Synthetic VCF Positions Must Be Valid for the Reference

**What goes wrong:** If `mini_ref.fa` has contig `22` with 100001 bases (extracted from 16000000-16100000), then VCF POS=16010100 is out of range for that contig (which only goes to position 100001). bcftools norm silently skips or errors.

**Why it happens:** The FASTA contig represents a subsequence, but bcftools norm uses the absolute POS value as an index into the contig.

**How to avoid:** Either (1) use positions 1-100000 in all synthetic VCFs (with contig named `22`), or (2) use the full chr22 reference. If approach (1): all VCF POS values, BED coordinates, and genome files must use the 1-100000 coordinate space consistently.

**Warning signs:** bcftools norm produces a VCF with identical sequences (no normalization applied), or reports "sequence not found" warnings.

### Pitfall 5: FORMAT/VAF Not Computed Without FORMAT/AD

**What goes wrong:** Synthetic VCFs with only `FORMAT/DP` (no AD) cause `bcftools +fill-tags` to skip VAF computation. All VAF-based filter expressions (`FORMAT/VAF<0.2`, etc.) evaluate to missing (`.`) and never trigger.

**Why it happens:** fill-tags documentation states VAF "requires FORMAT/AD or ADF+ADR".

**How to avoid:** Every synthetic VCF must include `FORMAT/AD` with the header `##FORMAT=<ID=AD,Number=R,Type=Integer,...>` and actual AD values in data rows.

**Warning signs:** `bcftools filter` log shows `FORMAT/VAF` as missing for all records; expected filtering doesn't happen.

### Pitfall 6: Freebayes INFO Fields Must Be Integer, Not Float

**What goes wrong:** Declaring `##INFO=<ID=SAF,Number=A,Type=Float,...>` but the filter uses `INFO/SAF==0` (integer equality). bcftools may emit type mismatch warnings or comparison behaves unexpectedly with floating-point zero.

**Why it happens:** SAF/SAR/RPR/RPL are read count integers in real Freebayes output. The `==0` comparison requires integer semantics.

**How to avoid:** Declare AO, SAF, SAR, RPR, RPL as `Type=Integer`.

### Pitfall 7: QUALperAO Division — Verify Arithmetic

**What goes wrong:** Filter `QUAL / INFO/AO < 10` requires AO >= 1. AO=0 causes divide-by-zero; bcftools treats it as missing, which may not trigger the filter as expected.

**How to avoid:** Always set AO >= 1 in synthetic VCFs. To trigger the filter: use QUAL=50, AO=8 (50/8=6.25 < 10). To pass: QUAL=200, AO=15 (200/15=13.3 > 10). Document the arithmetic in a comment in the VCF header.

### Pitfall 8: Expected Output Files Must Be Stable

**What goes wrong:** Expected output VCFs are generated at Phase 2 end, then regression tests in Phase 3 compare against them. If hardnormly.sh is modified between Phase 2 and Phase 3 for any reason, the expected outputs become stale.

**How to avoid:** Generate expected outputs at the VERY END of Phase 2, after all other tasks are done. Record the git commit hash in `tests/data/expected/BASELINE.txt`. Do not modify hardnormly.sh between generating expected outputs and running Phase 3 regression tests.

## Open Questions

1. **Coordinate scheme for synthetic VCFs and mini_ref.fa**
   - What we know: `samtools faidx hs37d5.fa 22:16000000-16100000` creates a 100kb FASTA; after header rename to `>22`, VCF positions must be 1-100000 to be within range for bcftools norm
   - What's unclear: Whether Phase 3 tests will need bcftools norm on synthetic VCFs (they test filtering, not normalization), or whether only the multiallelic.vcf needs normalization testing
   - Recommendation: Planner must decide: (a) use 1-100000 coordinate space for ALL synthetic VCFs (simpler mini_ref, but less intuitive positions), or (b) use chr22:16000000+ coordinates but skip bcftools norm for synthetic VCFs in CI (norm only tested via real data). Option (b) is likely simpler.

2. **Freebayes tiny VCF contig names**
   - What we know: q.vcf.gz is a real Freebayes output file with authentic Freebayes INFO fields; q.fa is a small custom reference; contig names and coordinates are unknown without downloading and inspecting
   - What's unclear: Whether freebayes_tiny.vcf.gz variants overlap with any chr22:16M-16.1M range, and what chromosome naming convention it uses
   - Recommendation: After downloading in generate_test_data.sh, run `bcftools view -h freebayes_tiny.vcf.gz` to inspect contigs. Tests using this file should NOT apply include/exclude BED files — use the freebayes_tiny_ref.fa that comes with it.

3. **gitignore *.vcf pattern scope**
   - What we know: `.gitignore` has `*.vcf` and `*.bed` patterns; after adding `!/tests/` exception, files in tests/ are no longer blocked by `*test*`, but `*.vcf` still matches any .vcf file including those in tests/data/
   - Recommendation: After fixing `*test*` with `!/tests/`, also add `!/tests/**/*.vcf` and `!/tests/**/*.bed` OR un-ignore the specific extensions within tests/. Verify with `git check-ignore -v tests/data/synthetic/gatk_sample_A.vcf` after the gitignore change.

4. **hs37d5 download size in generate_test_data.sh**
   - What we know: Full hs37d5 is ~3.4GB compressed; chr22 alone would be smaller; the script needs to extract a 100kb region from chr22
   - What's unclear: Whether to download full hs37d5 (slow but straightforward) or download just chr22 from a source that provides per-chromosome files
   - Recommendation: The 1000 Genomes provides per-chromosome reference files. Download only chr22: `https://ftp.1000genomes.ebi.ac.uk/vol1/ftp/technical/reference/phase2_reference_assembly_sequence/hs37d5.fa.gz`. This IS the full multi-chromosome reference (~3.4GB). Alternative: use the 1000G chr22-only reference at a different path. Given the script runs once and downloads are idempotent, downloading full hs37d5 is acceptable.
